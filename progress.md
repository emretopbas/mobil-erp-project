### 2026-10-03 — Cari Hesap: single-ledger architecture + RBAC: delete restricted to owner/manager

Two related pieces of user feedback acted on in one session: (1) a full rewrite of how account balances work, since the existing logic had drifted into multiple partial sources of truth; (2) only `owner`/`manager` should be able to delete made sales/orders, purchases, and entered payments, and the Personel screen needed a role-change control in the UI (the service already supported changing a role, there was just no button for it).

**Cari ledger rewrite**: every customer/account balance now comes from exactly one place — the append-only `cari_movement` table (Σ debit − Σ credit, in the contact's own currency), written only by `CariService`. Balances are never computed from orders, purchases, or the cash tables directly, and a correction is always a new `reversal` movement referencing `reverses_id`, never an edit/delete of an existing row. Event mapping: shipment → customer debit (net of discount, only once `shipped`); collection/customer return → credit; purchase received → account credit; payment/supplier return → account debit; bounced check → debit; a manual balance-close (`discount_close`, reason required, gated on a `cariClose` permission) nets against the balance. `reconcileSource()` makes shipment/purchase/check sync idempotent — re-running it against a changed source converges the ledger to the new desired amount rather than double-posting. Cash entry + its cari movement are written together in one `repository.transaction` (`FinanceService.createRevenue`/`createExpense`). Three former entry points (Para screen, customer/account screen, order's "Tahsilat ekle") were unified onto one `MoneyEntryForm`; "Kimden?/Kime?" is now mandatory with no silent default (a cari, an employee, or an explicit "Cari dışı" that requires a revenue category). Orders now store gross/discount/net separately, discount editable only pre-shipment. Also folded in this session: UI wording standardized to "Ödeme"/"Tahsilat" (never "ödeme yaptım/aldım") across every money screen, and the explanatory "Hesap sana borçlu"/"Sen hesaba borçlusun" sentences under balances were dropped in favor of plain red (we owe)/black (they owe) coloring — the user felt the prose was overstating how confusing the concept actually is for most people.

**RBAC — delete restricted**: new `DELETE_RESTRICTED_TO_OWNER_MANAGER` map in `src/services/rbac/permissions.ts` narrows just the `delete` action on `order`/`purchase` to owner/manager on top of their existing `crud` level (creating/editing stays open to sales/production as before). `finance` needed no new entry — production/sales/viewer already sit at `'none'` there, so voiding a payment was already owner/manager-only once `FinanceService.voidRevenue`/`voidExpense` existed (new this session: soft-deletes the entry + any linked `Check`, then calls `CariService.voidCashEntry` to reverse its cari effect). `src/app/employees.tsx` got an inline `RoleEditor` (radio list + Kaydet/Vazgeç) wired to the pre-existing `employeeService.update(id, {role})`, which already enforced the last-owner guard. Delete buttons on `orders.tsx`/`PurchasesScreen.tsx` now gate specifically on the `'delete'` action (not `'update'`), with a two-step confirm (a different warning when an order is already `shipped`); `CariLedgerView`/`MoneyScreen` only offer "Sil" on `cash_entry`-sourced rows, never on the auto-reconciled `shipment`/`purchase`/`return_*`/`discount_close` rows.

**Real bug caught by a new test, fixed before shipping**: `OrderService.softDelete` on a *shipped* order only reversed the cari debt, never the stock — a genuine gap, since nothing had put the stock back. Fixed by giving `setStatus`/`softDelete` one shared, idempotent `reconcileShipmentStock` (mirrors `PurchaseService.reconcileStock`'s diff-against-booked approach), which incidentally also fixed un-shipping (`shipped` → any other status) never restoring stock before. A sign-convention bug surfaced while writing the test for this (`desired` used a positive "shipped quantity" instead of the same negative inventory-delta sign `booked` uses, double-counting on re-shipment) — caught and fixed via `src/services/__tests__/OrderShipment.test.ts` before it ever reached the device.

**Verified**: on the user's real device data, view-only (opened each new confirm dialog, read it, cancelled — the one action actually executed was toggling a non-owner employee's role back and forth).

### 2026-09-09 — Keyboard-covering-form bug fixed on the admin module screens

User-reported bug: on `products.tsx`, opening the keyboard to fill in the per-product variant form (Varyant SKU/Beden/Renk) left the lower fields — especially "Renk" and the submit button — stuck behind the keyboard with no way to scroll them into view. Fixed in `ModuleScreen` (the shared shell every admin screen uses — Personel/Ürünler/Görevler/Gelir-Gider/Siparişler all inherit the fix, not just Ürünler).

First attempt (`KeyboardAvoidingView behavior="height"` on Android) wasn't enough — confirmed on-device the Renk field stayed unreachable no matter how far you scrolled. Root cause: the native manifest already sets `windowSoftInputMode="adjustResize"`, so stacking a `KeyboardAvoidingView` on top double-counts the keyboard height and shrinks the scrollable area more than necessary, leaving *less* room, not more. Real fix: dropped `KeyboardAvoidingView` on Android entirely (kept for iOS, which has no `adjustResize` equivalent) and instead track the live keyboard height via `Keyboard.addListener('keyboardDidShow'/'keyboardDidHide', ...)`, adding it as extra `paddingBottom` on the ScrollView's content — guarantees enough scroll room to bring even the last field in a long form fully clear of the keyboard, on top of whatever adjustResize already reclaimed.

**Verified thoroughly on-device** (not just by inspection — the first fix looked reasonable and turned out insufficient in practice): reproduced the user's exact scenario (Deri Canta -> + Varyant ekle -> focus Renk), confirmed before the second fix that scrolling maxed out with Renk and the submit button still behind the keyboard, then confirmed after the fix that both scroll fully into view. `tsc`/lint clean (same 45-problem pre-existing baseline, nothing new).

### 2026-09-04a — BackupService (§9 step 8) — Faz 1 checklist now fully closed

Picked up the one item left open on the §9 checklist. Discussed the encryption-key design with the user first rather than defaulting to either option: a **device-only key** was rejected (a device upgrade is the normal restore case for this app, not an edge case — a device-only key makes exactly that case unrecoverable) and so was a **user-remembered recovery passphrase** (adds a real "forgot my passphrase = data gone forever" failure mode for a threat — full account compromise — that already grants the same data through the app itself; no extra protection for the friction cost). Landed on: one random 256-bit key per business, generated once and stored in Firestore, restore driven purely by the same Firebase sign-in — no passphrase to remember or lose.

**Confirmed with the user why this doesn't reopen CLAUDE.md §2's Firestore ban**: that ban targets *operational* data (billed per-write, scales badly with transaction volume — the concern is the multiplication, not Firestore pricing being inherently worse). A per-business key document, written once and read occasionally, is exactly the "small config/metadata" carve-out §2 itself names — verified Firebase Storage's own billing model too (stored GB + egress + **coarse, file-level operations** — one backup upload/day is ~30 ops/month, nowhere near Firestore's per-document granularity either way).

**Built `src/services/BackupService.ts`**:
- `getOrCreateBusinessKey()` (module-private) — reads/creates `business_backup_keys/{businessId}` in Firestore; a real CSPRNG key via `expo-crypto`'s `getRandomBytesAsync(32)` (not `crypto-js`'s `WordArray.random()`, which silently falls back to `Math.random()` on RN with no `crypto.getRandomValues` polyfill — a real, easy-to-miss trap).
- `backupNow(ctx: ActorContext)` — RBAC-gated (`settings`/`update`, same gate as `SettingsService`, owner/manager only per §5.4). Reads the local SQLite file as base64 (`expo-file-system`'s new `File` API — synchronous-JSI-backed, note the async/sync method pairs: `base64()`/`base64Sync()` etc.), AES-encrypts it with `crypto-js` (passing the key as a passphrase string — CryptoJS's own OpenSSL-compatible KDF handles salting), uploads to `business_id/<timestamp>.enc` in Storage (§7.3's exact naming), updates `business.last_backup_at` (new migration 4 column, same "spec names it in prose, §4's table doesn't have it" pattern as migrations 2-3).
- `restoreLatest(businessId)` — lists the business's Storage folder, downloads the newest `.enc` (filenames are sortable ISO timestamps), decrypts, and **writes it back over the live SQLite file** — the one genuinely tricky part: this requires closing the cached db connection (`db/client.ts` gained a real, non-test-only `closeDbConnection()` — the old `_resetDbConnectionForTests` was truly test-only before, kept as a deprecated alias) *and* dropping the app-wide `Repository` singleton (`getRepository.ts` gained `resetRepository()`) — the Repository's table wrappers are bound to a specific `SQLiteDatabase` handle at construction time, so closing the raw connection alone left the existing Repository silently stale. Caught this only by tracing through `SqliteRepository`'s constructor, not by any test — worth flagging since it's exactly the kind of bug that would've looked fine in isolation and broken restore for real.
- `recordEmployeeBusinessMapping()` / `findBusinessForRestore()` — a second small Firestore collection, `employee_business_map/{firebase_uid} → {business_id}`, written once when `SessionProvider.createBusiness()` runs. This is what makes restore-on-a-genuinely-new-device possible at all: that scenario's whole problem is a signed-in Firebase user whose **local** SQLite is empty, so there's no Employee row yet to look up a business through — this Firestore pointer is the only thing that can bridge "who is this uid" to "which business's backup do I fetch" before any local data exists.

**Wired into the actual restore-on-new-device flow**, not just a callable method: `SessionProvider` gained `restoreFromBackup()`, valid only in `needs_business` — looks up the mapping, restores, resets+rebuilds the Repository singleton, re-resolves the session. `create-business.tsx` (the screen `needs_business` lands on) now offers "Yedekten geri yükle" above the normal create-business form, silently no-ops (no scary error) when nothing's on record, since a genuinely new signup hits this same screen. `(app)/explore.tsx` (Profil) got a "Şimdi yedekle" button (owner/manager only, same RBAC gate) plus a last-backup timestamp — the manual/on-demand half of backup, complementing the automatic restore-lookup half.
